## 配额解决什么问题

“同一目标同时最多一人出手”“同一扇门同时最多两人通过”（示例）这类限制，与谁担任什么职责无关，只关心同一时刻有多少人在做同一件事。配额服务 `UStellaCoordinationQuotaSubsystem` 管理这类限制：

- **池**：一个配额池资产（`ACQ_`）加一个作用域对象，确定一个池。池资产的 `Capacity` 是同一作用域内同时持有的权重上限，默认 1，不大于 0 时不限制。
- **申请**：持有者申请一组池，每个池带一个权重；获准后占用计入各池，归还时释放。
- **共用一套名额**：群体代成员申请和个体自己申请走同一套准入，不会互相绕过排队。

配额服务可以脱离协调实例单独使用，没有加入任何实例的 AI 也能申请。它和协调宿主一样，只在服务器或单机世界受理。

## 申请与归还

| 接口                             | 作用                                                                               |
| -------------------------------- | ---------------------------------------------------------------------------------- |
| `Request(Holder, Costs, bQueue)` | 为持有者申请一组池，返回申请身份；输入无效或在客户端调用时返回无效身份             |
| `Release(Claim)`                 | 归还持有中的配额，或撤回排队中的申请；重复或迟到的归还返回 `false`                 |
| `GetClaimState(Claim)`           | 申请状态：`Held` 持有、`Pending` 排队、`None` 不存在（从未受理、已归还或已被收回） |
| `GetUsage(Pool, Scope)`          | 某个池当前已持有的权重之和                                                         |

`Costs` 中每一项是 `FStellaCoordinationQuotaCost`：池资产 `Pool`、作用域 `Scope`（为空表示全局）和权重 `Cost`（默认 1）。

```cpp
// 示例：AttackSlots 是配额池资产，以目标为作用域，不排队
UStellaCoordinationQuotaSubsystem* Quota = UWorld::GetSubsystem<UStellaCoordinationQuotaSubsystem>(GetWorld());
FStellaCoordinationQuotaCost Cost;
Cost.Pool = AttackSlots;
Cost.Scope = Target;
const FStellaCoordinationQuotaClaimHandle Claim = Quota ? Quota->Request(this, {Cost}, false) : FStellaCoordinationQuotaClaimHandle();
if (Claim.IsValid())
{
	// 不排队时，有效的身份就表示已经持有；行动结束后调用 Quota->Release(Claim)
}
```

**一次申请多个池**：同一池出现多次时合并权重。所有池都放得下才一起持有；只要有一个放不下，其他池也不占用。

## 排队与阻挡

排队的申请在配额服务每次更新时按先后授予：

- **新申请排在已有排队者之后**：只要涉及的池中已有排队者，新申请即使放得下也不会插队，避免小申请反复插到大申请前面。
- **排队者挡住后来者**：一个排队申请还没获准时，它涉及的每个池中排在它后面的申请都要等待。
- **其他池不受影响**：不涉及这些池的申请照常授予。

例如一个池容量为 2，A 持有 1；B 排队申请 2，放不下；C 随后申请 1，虽然放得下，也要排在 B 后面。A 归还后 B 获准，B 归还后 C 才获准（示例）。

调试面板会列出每个池的持有者、排队者、已等待时长和阻挡原因，见[调试与排查](/read/stellacoordination-debugging#coordination-面板)。

## 失效收回与通知

- **弱引用登记**：持有者以弱引用登记。持有者、作用域对象或池资产失效时，申请在下一次更新中被收回，占用随之释放。
- **状态变化通知**：C++ 可以订阅 `OnClaimChanged`。排队的申请获准、或申请被收回时，配额服务在本次更新的状态全部改完后同步通知。观察者不要在回调中申请或归还配额。

## 职责代成员持有

职责资产的 `Quotas` 列出担任这个职责期间要持有的配额，每项是一个池和权重。宿主以成员的名义代为申请：

- **作用域是安排的目标**：需求没有指定目标时依次取共享目标、键对象，所以总有作用域。同一池资产在每个目标下都是独立的池。
- **全部获准才投递**：配额获准之前，安排保持已提出，成员看不到。
- **配额被收回时撤回**：代持的配额被配额服务收回时，安排随之撤回。
- **停止期间继续计数**：已采用的安排被请求停止后，代持的配额继续计数，直到执行侧报告结束。
- **目标改变时重新申请**：职责或目标改变时，安排重新提出，配额按新的作用域重新申请。

例如给“出手”职责配上容量为 1 的攻击名额池（示例），每个目标同时只有一名担任者真正收到安排，其余担任者的安排停在已提出、排队等待。

<Note title="代持配额与个体配额共用一个池">

如果不在协调中的 AI 也要遵守同一个限制，让它以同一池资产、同一目标为作用域自己申请。两边进入同一个池、同一条队列，按先后获准。

</Note>

## 成员自己申请

成员可以在执行职责时自己申请配额：

- **C++ 或蓝图**：直接调用 `Request` 与 `Release`，持有者通常是成员自己。
- **成员 StateTree**：用 `Coordination Hold Quota` 任务在状态内成对申请与归还。

`Coordination Hold Quota` 的字段：

| 字段     | 含义                                                    |
| -------- | ------------------------------------------------------- |
| `Pool`   | 配额池资产                                              |
| `Scope`  | 作用域，可以绑定，例如绑定到安排的目标；为空表示全局    |
| `Cost`   | 权重，默认 1                                            |
| `bQueue` | 为否时放不下即失败；为是时排队，获准后输出 `bHeld` 为真 |
| `bHeld`  | 输出：当前是否已经持有                                  |

任务进入状态时以成员为持有者申请，退出状态时归还；申请被收回时任务失败。所在状态被重新选中时，不会重复申请或提前归还。

## 当前的限制

配额服务目前只有权重容量、立即与排队准入、按先后授予和失效收回。租期续期、冷却、锁定、抢占、超额处理、容量倍率与覆盖，以及按小队等组织单位划分的作用域，都还没有实现。

代码位置（插件 `Source/StellaCoordination`）：`StellaCoordinationQuotaSubsystem`（申请、排队与收回）、`StellaCoordinationQuotaPoolDefinition`（池资产与申请项）、`StellaCoordinationRoleDefinition`（职责的 `Quotas`）、`StateTree/StellaCoordinationSTTask_HoldQuota`。
