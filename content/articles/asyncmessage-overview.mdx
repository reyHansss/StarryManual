## 它适合做什么

Async Message System 是 UE 5.8 自带的插件：

- **消息身份**：用 Gameplay Tag 标识；
- **消息数据**：用结构体承载；
- **发送方**：不需要知道谁在接收；
- **接收方**：提前登记监听，在自己的接收阶段处理消息。

Starry 用它发布“已经发生了什么”，例如技能激活失败、受到伤害、被淘汰、玩家重置、背包与快捷栏变化，供界面刷新、事件提示和解耦的观察者使用。现有消息及其触发位置见[项目消息与排查](/read/asyncmessage-project)。

**它不适合**：

- 需要立刻拿到返回值；
- 需要明确调用某个对象；
- 执行权威的玩法命令。

这些情况直接调用对应领域的接口。例如 [Input Handler](/read/input-handlers) 直接调用移动和 GAS，不经过消息。

## 接入前先定四件事

| 要定的事 | 内容                                                                              |
| -------- | --------------------------------------------------------------------------------- |
| 消息身份 | 一个已注册的 Gameplay Tag，例如 `Starry.Damage.Message`，封装为 `FAsyncMessageId` |
| 载荷约定 | 这个标签对应的结构体及字段含义，例如 `FStarryVerbMessage`，发送和接收双方保持一致 |
| 路由范围 | 同一个 World、同一个 Endpoint。项目现有的发送都使用默认的 World Endpoint          |
| 监听寿命 | 什么时候开始、由谁保存任务或句柄、什么时候停止；避免每次刷新界面都重复登记        |

**启用情况**：插件已经启用，`StarryGame` 与 `StarryEditor` 已加入模块依赖。

- **蓝图**：直接使用 `Start Listening for Async Message` 和 `Queue Async Message for Broadcast`，不需要手工创建消息子系统。
- **C++**：其他 C++ 模块要用插件接口时，在自己的 `Build.cs` 中加入 `AsyncMessageSystem`。

## 默认的派发时机

- **默认接收时机**：蓝图监听默认在**游戏线程的 `TG_PostUpdateWork`** 接收。
- **入队不等于派发**：入队时不会同步执行监听者，回调发生在对应队列下一次被处理时：可能是当前帧，也可能是之后的帧，不要依赖固定的延迟或“一定是下一帧”。
- **C++ 的其他选项**：C++ 可以选择其他 Tick Group（支持 `TG_PrePhysics` 到 `TG_PostUpdateWork`）、命名线程或任务优先级。在后台线程接收时，要自己遵守线程约束。
- **同一队列中的顺序**：后入队的消息先派发。同一帧多条消息的先后有意义时，用消息的 `GetSequenceId()` 排序。
- **游戏暂停时**：消息系统的 Tick 没有设置为暂停时也运行。按代码推断，游戏暂停期间不会派发消息，这一点没有经过运行验证。

## 边界

- **不跨 World，不联网**：每个 World 有独立的消息系统。PIE 中服务器世界和客户端世界不会因为标签相同就互通，插件也不会把消息变成 RPC。要跨网络，先由状态复制或显式 RPC 把数据送到接收端，再在接收端的 World 内发布。
- **不保存历史**：没有人监听时，消息不会被留着等后来的订阅者。界面打开时，先登记监听，再从领域接口读取当前状态，之后用消息更新。
- **插件仍是 Experimental**：本机 UE 5.8 的插件描述中仍标为 Experimental，升级引擎时需要复核接口和行为。
