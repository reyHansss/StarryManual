## 一次配对怎样进行

每次实例更新推进群体树之后，宿主立即配对一次：

1. **收集候选**：可指挥且可用的成员参与配对。登记时 `bCommandable` 为否的成员留在实例中，但不会被安排。
2. **逐项评估**：对每名成员 × 每项需求，判断能否担任，能担任时计算代价。
3. **按优先级贪心选取**：需求按 `Priority` 从高到低分组处理。同一优先级的需求在剩余名额内反复选出代价最小的“成员 × 需求”组合，直到名额用完或没有可担任的成员。
4. **提交差异**：配对结果与上一次相同的安排保持原身份，不重新投递；不再需要的安排撤回；新的配对提出新安排。

高优先级的需求先挑人，所以新激活的高优先级职责会从低优先级职责中拉走合适的成员。同样的输入总是得到同样的结果，代价相同时按固定顺序取先者。

“被冻结挡住”指两种情况：需求已冻结而这名成员不是它的担任者；或者这名成员正担任另一项冻结需求。调试面板中，不可担任的成员显示下面的原因：

| 原因         | 何时出现                                                                          |
| ------------ | --------------------------------------------------------------------------------- |
| 已耗尽       | 职责在本实例中已耗尽                                                              |
| 冻结中       | 被冻结挡住                                                                        |
| 一次性已分配 | 一次性分配的需求已经完成首次配对，这名成员不是担任者                              |
| 冷却中       | 这名成员对该职责的上一项安排未被采用或执行失败，冷却时长等于职责的 `OfferTimeout` |
| 标签不符     | 不满足职责任务的 `Eligibility`                                                    |
| 条件的类名   | 某个成员条件不满足，面板显示这个条件的类名                                        |
| 代价无效     | 代价不是有限值                                                                    |

## 代价：谁更合适

**默认按距离**：职责任务没有代价项时，成员代价是它到职责目标的距离，单位厘米，越近越优先；没有目标时为 0。

**代价项**：填写 `CostTerms` 后，成员代价为各项“`Weight` × 评估值”之和。插件自带 `Distance To Target`，评估值就是上面的距离；权重取负数时，越远越优先。例如“侦察”职责可以同时使用一个业务代价项（权重 1）和 `Distance To Target`（权重 0.5）（示例）。

**成员条件**：填写 `Conditions` 后，全部条件满足才可担任。插件不自带成员条件，按业务需要在蓝图或 C++ 中派生。

**标签资格**：`Eligibility` 读取参与者 Actor 的 GameplayTag，Actor 要实现 `IGameplayTagAssetInterface`（`AStarryCharacter` 已实现），没有实现时视为不带标签。

成员条件与代价项收到同一份查询 `FStellaCoordinationMemberQuery`：

| 字段         | 内容               |
| ------------ | ------------------ |
| `Member`     | 被评估的成员 Actor |
| `Instance`   | 所在的协调实例     |
| `Role`       | 需求的职责         |
| `Target`     | 需求解析后的目标   |
| `Parameters` | 需求的业务参数     |

在蓝图中派生时，成员条件实现 `IsEligible`，代价项实现 `Evaluate`。

<Note title="成员条件与代价项只做判断">

它们是群体树节点上的内联对象，被所有配对共享，而且每次配对都会被调用。只读取查询与领域状态，不要在里面修改宿主、申请配额或保存某次查询的状态。

</Note>

## 保持优势：避免来回换人

现任担任者参与配对时，它的代价先扣除保持优势再比较。保持优势默认取模式的 `AssignmentKeepBonus`（默认 500，与代价同单位）；职责任务勾选 `bOverrideKeepBonus` 时改用任务自己的 `KeepBonus`。

例如按默认的距离代价：现任离目标 900 厘米，扣除 500 后按 400 比较。新人要离目标近于 400 厘米才会接替；只近一点点，不会换人。

## 分配设置

职责任务上的分配设置改变配对的规则，并在树视图的任务摘要中列出。

### 冻结

`bFrozen` 可以绑定到群体事实，例如首领阵亡后冻结外围职责（示例）。冻结期间：

- 担任者固定在这项需求上，不调到别的需求，也不按资格与代价重新评估；
- 名额按现有担任人数计，非担任者不能调入；
- 担任者离开或死亡后，名额不会补上。

### 一次性分配

勾选 `bOneTimeAssignment` 后，所在状态每次激活后，首次配对选中成员即关闭：之后只保留现有担任者，空出的名额不补。状态下一次激活时，新登记的需求重新开放。

### 按组捆绑

勾选 `bBundleByGroup` 后，需求以组为单位挑人：

- **配对单位**：同组中还没被其他需求选走的成员组成一个单位。其他需求指优先级更高、或同一优先级中先被选中的需求。没有组的成员自成一个单位。
- **可选条件**：单位中的成员全部可担任，而且人数不超过剩余名额，才可以选。
- **单位的代价**：成员代价（扣除保持优势后）的平均值。
- **与普通需求并存**：没有捆绑的需求仍按单人配对，可以选走组内的个别成员。

组来自项目接入的组织事实来源：在 C++ 中调用宿主的 `SetParticipantGroupResolver`，按参与者 Actor 返回组名，`NAME_None` 表示不属于任何组。宿主每次配对时查询，不保存成员表。

```cpp
// 示例：FindSquadName 是业务提供的小队查询
Host->SetParticipantGroupResolver(FStellaCoordinationParticipantGroup::CreateLambda(
	[](const AActor& Participant)
	{
		return FindSquadName(Participant);
	}));
```

Starry 还没有设置组织事实来源，目前每名成员自成一组。

### 耗尽

耗尽按职责记录在实例中，跨所在状态的多次进入保留。满足任一条件时职责耗尽：

| 设置                                       | 触发条件                                                                    |
| ------------------------------------------ | --------------------------------------------------------------------------- |
| `ExhaustAfterDeaths`                       | 担任这个职责期间失效（例如死亡）的累计人数达到该值；0 表示不启用            |
| `bExhaustByLiving` 与 `ExhaustLivingCount` | 本次激活中，存活的担任人数曾经多于 `ExhaustLivingCount`，之后降到该值或以下 |
| `bExhaustOnExit`                           | 所在状态退出、需求被撤销时                                                  |

例如 `ExhaustLivingCount = 1`：担任者曾经有 2 人以上，后来只剩 1 人时，职责耗尽（示例）。

**耗尽之后**：

- 需求名额变为 0，现有担任者在本次提交中撤回；
- 之后同一职责登记的需求也不再招人；
- 首次耗尽时，向群体树发出 `StellaCoordination.Event.Role.Exhausted` 事件；
- 耗尽优先于冻结。

**计数的细节**：

- **死亡数**：在安排结束时累计。已经请求停止的安排失效不计入；交接期间同一名成员只计一次。
- **存活峰值**：按需求的每次激活重新记录；状态退出时撤回担任者不算减员。
- **判断时机**：按死亡数和存活人数的判断在每次配对之前进行。

`Coordination Role Exhausted` 条件和职责任务的 `bExhausted` 输出都可以读到耗尽结果，用法见[群体树](/read/stellacoordination-group-tree#读取协调结果条件与评估器)。

代码位置（插件 `Source/StellaCoordination`）：`StellaCoordinationRoleSolver`（贪心配对）、`StellaCoordinationSubsystem`（候选评估、分配设置与耗尽）、`StellaCoordinationMemberRules`（成员条件、代价项与 `Distance To Target`）。
