## 它解决什么问题

攻击动画的后半段，玩家往往会提前按下一次攻击或闪避。如果立刻执行，会打断当前动画；如果直接丢掉，操作会显得迟钝。

输入缓存的做法：在动画指定的一段**窗口**内，把可缓存的输入先存起来，窗口正常结束时再执行；动画被打断，就丢弃它们。

**由谁提供**

- 缓存由 `UStarryInputBufferComponent` 提供，InputManager 继承了它。
- 窗口由动画通知状态 **Input Buffer**（`UStarryAnimNotifyState_InputBuffer`）打开和关闭。
- 缓存的保留时间由窗口决定，单条输入没有单独的过期时间。

## 配置一个动画窗口

1. 给需要延后执行的 Handler 打开 `bCanBeBuffered`。它的 `BufferChannelTag` 默认就是 `Input.Buffer.Channel.Default`。
2. 确认 Manager 的 `InputBufferMode` 已启用，默认是 `LastCommand`。
3. 在 Montage 上添加 **Input Buffer** 通知状态，覆盖需要缓存的时间段。通知的通道默认也是 `Input.Buffer.Channel.Default`，所以只用一个通道时，两边都不用改。
4. 验证两种情况：
   - 正常播放到窗口结束，保留的命令被执行；
   - 中断 Montage，这个窗口里的命令被丢弃。

**其他限制**

- 这个通知只能放在 Montage 上，并且只对本地控制的角色生效。
- 需要多个互不影响的窗口时，给 Handler 和通知设置不同的通道标签。
- 工程资产中目前还没有 Montage 使用这个通知。

## 首批与末批

| `InputBufferMode`     | 窗口内每个通道保留什么                       |
| --------------------- | -------------------------------------------- |
| `LastCommand`（默认） | 最新的一批命令，覆盖这个通道之前的一批       |
| `FirstCommand`        | 第一批命令；之后同通道的输入被丢弃，不会执行 |
| `Disabled`            | Manager 不使用自己的缓存                     |

**“一批”的含义**：一次动作事件可能分派给多个 Handler。系统先按各 Handler 的通道分组，同一通道里保持原来的顺序，这些命令就是“一批”。首批、末批模式选的是这一整批，不是只执行其中一个 Handler。

**通道之间互不影响**：不同通道互不覆盖。窗口按精确标签匹配，不能用父标签推断所有子通道都已打开。

**`Disabled` 不等于没有缓存**：这时 Manager 会改用宿主上其他已启用的缓存组件；没有其他缓存组件时，所有处理器都立即执行。

## 正常结束与中断

/>

- **`OpenInputBuffer(ChannelTag)`**：打开窗口。
- **`CloseInputBuffer(ChannelTag, false)`**：执行这个通道保留的命令，再移除通道与命令。
- **`CloseInputBuffer(ChannelTag, true)`**：直接丢弃。

通知结束时用 UE 的 `NotifyStateReachedEnd(EventReference)` 判断是否真的播放到了末尾，能正确处理播放速率变化和 Montage 中断。共享的通知资产里不保存每个角色的计时。

同一通道没有嵌套计数。两个重叠的窗口如果用同一个通道，先关闭的那个会提前结束另一个。

## 不应该留下旧输入

- **清空**：`ResetInputBuffer` 清空全部通道与命令。停用输入处理、移除 Setup 时都会清空缓存，避免角色或功能退出后又冒出旧命令。
- **执行时再判断**：缓存保存的是动作与输入值的快照，真正执行时仍然回到 Handler，再调用领域能力。技能还能不能激活、目标是否仍然有效，由执行那一刻的领域规则判断。
- **直接调用接口时**：底层的 `OpenInputBuffer` 只登记通道，不检查是否处于 `Disabled`。自定义代码直接调用这些接口时，先用 `IsInputBufferEnabled` 查询，并自己保证打开与关闭的顺序。

Handler 的共享规则见 [Handler 与能力分派](/read/input-handlers)，缓存没有生效时见[调试与排查](/read/input-troubleshooting)。
