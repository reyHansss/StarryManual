## 状态与结束原因

宿主每提交一项新的配对，就提出一项安排。安排带有唯一身份 `FStellaCoordinationAssignmentHandle`，执行侧之后的每次报告都要带上它。

| 状态   | 含义                                                                 |
| ------ | -------------------------------------------------------------------- |
| 已提出 | 已配对，等待代持的配额获准，或等待成员的上一项安排结束。成员看不到它 |
| 已投递 | 已经交给成员的个体决策，尚未被采用                                   |
| 已采用 | 个体决策已经接下这项安排                                             |
| 已开始 | 执行侧报告实际行动开始。没有单独报告采用时，报告开始也算作采用       |

图中省略了撤回与失效：安排在任何状态下都可能被撤回或失效，规则见下文。安排结束后，宿主立即删除记录：按身份查询返回空，状态为 `None`。

| 结束原因 | 何时出现                                                 | 之后                         |
| -------- | -------------------------------------------------------- | ---------------------------- |
| 成功     | 执行侧报告 Succeeded                                     | 计入需求的成功次数           |
| 失败     | 执行侧报告 Failed，表示业务失败                          | 成员对该职责冷却             |
| 中断     | 执行侧报告 Aborted，例如被更高优先的行为打断             | 无                           |
| 未采用   | 投递失败，或投递后超过职责的 `OfferTimeout` 仍未被采用   | 成员对该职责冷却             |
| 撤回     | 协调方撤回；已采用的安排在执行侧确认停止后，才以撤回结束 | 无                           |
| 失效     | 参与者已销毁、被判定不可用或被注销，不等待执行侧确认     | 担任期间失效计入职责的死亡数 |

**冷却**：未采用或失败之后，这名成员在 `OfferTimeout`（默认 5 秒）内不再配对这个职责。否则一进入就失败的成员会在每次更新中被重新配回来，反复循环。

**成功次数**：职责任务的 `CompleteAfterSuccesses` 为正时，需求累计这么多次成功后，任务以成功结束，群体树可以据此切换阶段。

## 执行侧怎样报告

执行侧通过宿主的报告接口推进安排，每次都按完整的安排身份报告：

| 接口                       | 作用                                                                                   |
| -------------------------- | -------------------------------------------------------------------------------------- |
| `ReportAccepted`           | 已投递 → 已采用                                                                        |
| `ReportStarted`            | 已投递或已采用 → 已开始                                                                |
| `ReportProgress(Progress)` | 记录一个进度标签（例如“到位”），并把这个标签作为事件发给群体树                         |
| `ReportEnded(Result)`      | 报告结束，结果通常是 Succeeded、Failed 或 Aborted；请求停止之后报告的 Aborted 记为撤回 |

- **身份不对就拒绝**：已结束、迟到或重复的报告返回 `false`，不会改动其他安排。已提出的安排还没交给成员，对它的报告也会被拒绝。
- **状态立即改变**：宿主收到报告就改变状态，对应的事件在实例下一次更新时送达群体树。
- **查询**：`GetAssignment` 读取未结束安排的副本，`GetAssignmentState` 读取状态，`FindAssignmentOf` 按参与者找它当前的安排。

使用自带的投递方式时，这些报告由接入代码代为完成：StellaUtilityAI 命令的领取与结束、成员侧 StateTree 节点的进入与退出，都会转成对应的报告，见[成员接入](/read/stellacoordination-members)。

## 撤回与收回投递

配对结果不再需要某项安排时（需求撤销、名额减少、被别人接替），宿主撤回它，并通知投递方式收回：

- **还没被采用**：已提出与已投递的安排立即以撤回结束。宿主先删除记录，再通知投递方式；投递方式在收回过程中同步报告的结束会被拒绝，不会改写结束原因。
- **已经采用**：只请求停止。安排上的 `bRevokeRequested` 变为真，投递方式收到通知（例如撤销命令），然后等执行侧报告结束。在这之前，代持的配额继续计数。
- **正常结束之后**：宿主在下一次更新中收回投递对象。例如 `Utility AI Command` 会撤销命令，避免同一成员再次接取已经结束的安排。

<Note title="请求停止不等于已经停止">

宿主不会因为发出了停止请求，就认为执行已经停止。执行侧必须自己发现停止请求，走完取消与清理，再报告结束。成员侧的持有任务会在发现停止请求时退出状态，并报告中断。

</Note>

## 投递超时

安排投递后，执行侧要在职责的 `OfferTimeout` 内采用它，否则记为未采用。投递方式返回失败时，也立即记为未采用。超时只针对“已投递、还没采用”的安排；已采用的安排没有执行时长的限制，由执行侧决定何时结束。

## 职责或目标改变

需求激活期间，职责任务的字段可能因为绑定而变化，宿主按变化的内容处理已有安排：

| 改变的内容                     | 已有安排怎样处理                                                               |
| ------------------------------ | ------------------------------------------------------------------------------ |
| 职责或目标（例如共享目标换人） | 撤回，再对同一名成员按新设置重新安排；代持配额按新职责与新目标的作用域重新申请 |
| 业务参数                       | 就地更新，不撤回、不重新投递；执行侧按安排身份读取最新值                       |
| 容量、优先级、资格、条件、代价 | 影响下一次配对的结果；配对结果不变的安排保持原身份                             |

## 一名成员同时只收到一项安排

如果成员还有一项已投递、尚未结束的安排（例如正在等待停止确认的旧安排），新安排先建立，保持已提出，成员看不到。旧安排结束后，宿主在下一次更新中投递新安排。

交接期间：

- **计为新职责的担任者**：成员已按新安排计入担任人数，冻结、一次性分配和按存活人数耗尽不会因为交接而丢掉这名成员。
- **查询返回旧安排**：`FindAssignmentOf` 返回已投递的旧安排，成员侧节点也只看得到它。
- **失效只计一次**：交接期间成员失效，职责的死亡数只计一次。

## 成员离开、失效与实例结束

| 发生的事                                                             | 安排怎样结束                                                                 |
| -------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 调用 `Leave` 让成员离开                                              | 未采用的安排立即撤回，已采用的请求停止并等待确认；执行成员附加处理的离开回调 |
| 参与者失效（Actor 销毁、被判定不可用）或调用 `UnregisterParticipant` | 全部安排收回投递后以失效结束，不等待确认；参与者离开所在实例                 |
| 实例结束（没有成员、键对象不可用、群体树停止）                       | 先停止群体树，再撤回全部安排，并执行全部成员的离开回调                       |
| 代持的配额被配额服务收回                                             | 安排被撤回                                                                   |
| 世界关闭                                                             | 停止群体树后直接清空，不回调执行侧与成员附加处理                             |

**观察安排结束**：C++ 可以订阅宿主的 `OnAssignmentEnded`，它在安排结束时同步通知结束前的记录与结束原因。观察者只做记录或统计，不要在回调中修改宿主。

代码位置（插件 `Source/StellaCoordination`）：`StellaCoordinationTypes`（安排、状态与结束原因）、`StellaCoordinationSubsystem`（报告接口、撤回、超时、交接与收尾）、`StellaCoordinationExecution`（投递方式的投递与收回）。
